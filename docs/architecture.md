# Архитектура xray-ctl

Это описание текущих исходников, а не гарантия одинаковой работы в каждой
сети. Нормативные критерии находятся в [REQUIREMENTS.md](../REQUIREMENTS.md).

## Компоненты и поток данных

```text
именованные подписки → обновление/кэш → параллельные проверки → выбранный профиль
                                                     ↓
приложение → системная таблица 4269 → blanc0 (TUN) → Xray routing
                                                    ├─ direct → физический интерфейс
                                                    ├─ proxy  → выбранный VLESS-узел
                                                    └─ block
```

`app/blancctl.py` — CLI, парсер подписок, кэш, выбор узла и правила Xray.
`blancctl.service` запускает Xray с TUN и SOCKS на `127.0.0.1:10808`.
`lib/tun-route` создаёт IPv4/IPv6 policy route: публичные назначения попадают
в `blanc0`, а локальные/частные подсети проходят через обычную таблицу.
`blancctl-failover.timer` запускает проверку соединения после предыдущего
прохода. Arch настраивает владельца и timer через `xray-ctl-setup`; в NixOS
эту роль выполняет модуль `services.xrayCtl`.

## Подписки и выбор

Именованные подписки обновляются параллельно. Точные дубликаты соединения
объединяются с сохранением списка источников; разные параметры подключения
остаются отдельными профилями. Исчезнувшие при обновлении профили остаются
резервными. `update` не меняет работающий VPN. `best` сначала использует кэш,
проверяет четыре сайта для каждого кандидата, сравнивает задержку, затем
использует скорость только как дополнительный показатель среди близких по
доступности узлов. Обновление подписки после обычного `best` идёт в фоне.

Таймер следит за живым SOCKS-путём и маршрутом TUN. Он не переподключает VPN
после явного `stop`; единичный сетевой сбой не переключает узел. Неудачный
выбор нового узла должен вернуть прежнюю конфигурацию. Автоматический failover
может кратко разорвать текущие соединения.

## Где хранится состояние

`/var/lib/blancctl` — приватный каталог владельца, в нём находятся URL
подписок, полученные профили, выбранный узел, правила маршрутизации и
генерируемый `xray.json`. Не копируйте этот каталог в публичный репозиторий и
не передавайте его целиком для отладки. Публичные исходники не содержат URL
подписок и VLESS-ключей.

`events.jsonl` и его четыре ротируемые копии содержат ограниченные по объёму
диагностические события приложения. `xray-ctl log` читает их; `xray-ctl log
--service` показывает сообщения Xray и таймера из systemd journal. В отличие
от событий приложения, сохранность systemd journal после перезагрузки
зависит от конфигурации хоста. Не публикуйте даже диагностические файлы без
просмотра: системный журнал Xray может содержать больше деталей.

## Границы безопасности

Только небольшая команда service-control вызывается через узкое правило
`sudo`; обычный `xray-ctl` не запускается от root. Xray получает сетевые
capabilities, нужные для TUN. При остановке VPN это **не** режим «запретить
весь трафик»: система может использовать обычный маршрут. Резолвер DNS и
поведение браузера (включая собственный DNS и QUIC) требуют отдельной
проверки. Подробности правил и воспроизведение ошибки `cldom.ru` — в
[руководстве по раздельному туннелированию](split-tunneling.md).
