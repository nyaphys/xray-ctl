# Раздельное туннелирование: настройка и проверка

Рабочая модель xray-ctl: публичный трафик по умолчанию попадает в TUN
`blanc0`, после чего **Xray**, а не `curl` и не таблица Linux, выбирает
`direct`, `proxy` или `block`. Приватные/LAN-сети исключены раньше, на уровне
policy routing. Правила Xray хранятся локально и применяются при следующем
выборе узла или по `xray-ctl route apply`.

## Что означают правила

| Правило | Поведение |
| --- | --- |
| `direct` | Xray подключается к назначению через физический интерфейс. |
| `proxy` | Xray отправляет соединение через выбранный VLESS-узел. |
| `block` | Xray отклоняет соединение. |

Для публичных назначений приоритет `block` → `proxy` → `direct` → режим по
умолчанию (`proxy`). Поэтому явное `proxy`-правило может перекрыть более
широкое `direct`-правило. `domain:example.ru` охватывает домен и поддомены;
`full:example.ru` — только точное имя. Значение без префикса нормализуется
в `domain:`. `geosite:NAME` использует встроенный в Xray список доменов
сервиса. Начиная с 0.6.13 российские назначения по умолчанию идут
напрямую, остальной публичный трафик — через VPN:

| Прямое правило | Зачем |
| --- | --- |
| `domain:ru`, `domain:xn--p1ai` | `.ru` и `.рф`, включая поддомены. |
| `geosite:category-ru` | Российские сервисы в иных доменных зонах и других российских TLD. |
| `geoip:ru` | Российские IP, включая соединения без видимого имени. |
| `geosite:ozon`, `domain:cldom.ru` | Сохранённые прежние исключения. |

Для домена, который не совпал с доменными правилами, Xray использует
`IPIfNonMatch`: проверяет адрес через DNS/GeoIP перед отправкой в VPN.
Это приближённая классификация, а не гарантия, что каждый российский сайт
будет найден или что каждый найденный сайт откроется напрямую. Например,
чужой сервис на российском IP тоже может уйти напрямую. Для отдельного сайта
можно задать более приоритетное `proxy`-правило.

```console
xray-ctl route show
xray-ctl route add direct domain example.ru
xray-ctl route add proxy domain full:login.example.ru
xray-ctl route add proxy domain full:blocked.example.ru
xray-ctl route add block ip 203.0.113.7
xray-ctl route apply
```

`route add` сохраняет правило в приватной конфигурации, но **не меняет живой
маршрут немедленно**. `route apply` проверяет конфигурацию и перезапускает
Xray; существующие соединения могут кратко оборваться. Она требует, чтобы
служба осталась активной, но не откатывает корректное правило только из-за
того, что уже выбранный VPN-узел не проходит проверку SOCKS/TUN. Живую
доступность сайта проверяйте отдельно. При неудаче запуска прошлая живая
конфигурация восстанавливается, но новое правило остаётся сохранённым.
Удаляйте ошибочное правило явно через `route remove ...` и применяйте снова.

## Ozon: правило для сервиса, а не одного имени

16 октября 2026 года `www.ozon.ru` ответил HTTP 307 напрямую через `wlan0`,
тогда как через прежний путь xray-ctl был таймаут. В 0.6.12 по умолчанию
добавлен `geosite:ozon`: Xray направляет напрямую связанные домены Ozon из
своего списка, в том числе `ozon.ru`, `o3.ru`, `o3t.ru` и
`ozonusercontent.com`. Это не гарантирует загрузку каждого ресурса браузера:
список зависит от установленной базы Xray, а недоступный напрямую отдельный
хост может всё ещё помешать странице. На изолированной проверке Xray
26.2.6 правило выбрало `direct` и `www.ozon.ru` ответил HTTP 307; чужой
домен попал в `block`. Установленная служба и браузер после обновления пока
не проверялись.

```console
xray-ctl route show
xray-ctl route apply
xray-ctl route test ozon.ru
```

Если на вашей сети Ozon должен идти через VPN, добавьте более приоритетное
`proxy`-правило для нужного домена. Удаление одного `geosite:ozon` больше
не переключит Ozon на VPN: остаются общие российские правила. При сбое
прямого пути для любого российского сайта `route test DOMAIN` покажет
сравнение, а `route add proxy domain DOMAIN` задаст точечный обход.

## Случай cldom.ru: что действительно установлено

Проверка 2026-10-09 на одной сети дала следующее:

| Путь | Результат |
| --- | --- |
| DNS | `cldom.ru` успешно разрешился в публичный IPv4 (адрес может измениться). |
| Системный маршрут | `ip route get` выбрал `blanc0`, таблицу `4269`. |
| Обычный `curl --noproxy '*'` и SOCKS Xray | Оба завершились таймаутом около 4 с. |
| `curl --interface wlan0` через физическую сеть | HTTP 200 примерно за 0,29 с. |

Это проблема **поведения раздельного туннелирования в данной сети**: сайт,
доступный напрямую, не открывается через путь xray-ctl. Приватные правила не
проверялись: прямое исключение могло отсутствовать, перекрываться другим
правилом или не срабатывать в этом соединении. Причина таймаута также не
установлена. Версия 0.6.4 добавляет проверенное для этой сети исключение
`domain:cldom.ru` по умолчанию, в том числе для поддоменов. Его можно удалить
командой `xray-ctl route remove direct domain cldom.ru`; пользовательские
`proxy`/`block` правила имеют более высокий приоритет. Важно: `--noproxy '*'`
отключает лишь HTTP/SOCKS-прокси приложения; системное правило Linux всё ещё
может направить такой запрос в `blanc0`. Поэтому его нельзя считать
доказательством прямого подключения.

После установки 0.6.4 проверьте `xray-ctl route show`. Если `proxy`/`block`
не перекрывает исключение, примените конфигурацию и выполните диагностику:

```console
xray-ctl route show
xray-ctl route apply
xray-ctl route test cldom.ru
```

После применения нужно проверить сайт в браузере **и** через SOCKS Xray:

```console
curl --noproxy '' --proxy socks5h://127.0.0.1:10808 \
  --connect-timeout 4 --max-time 12 -L -o /dev/null -sS \
  -w 'HTTP %{http_code}; total %{time_total}s\n' https://cldom.ru/
```

Разовая проверка 2026-10-12 получила HTTP 200 через физический интерфейс,
SOCKS и TUN, но пользователь по-прежнему наблюдает сбои. Поэтому этот результат
**не подтверждает устойчивую работу** и не показывает, какое именно правило
выбрал Xray: приватная конфигурация не читалась. Если правило уже было или
проверка снова даст таймаут, надо установить, распознал ли Xray домен в
TUN-трафике, нет ли более приоритетного правила и работает ли `direct`
outbound. Для возврата исходной политики после добавления правила:

```console
xray-ctl route remove direct domain cldom.ru
xray-ctl route apply
```

## Как отличить классы неисправностей

1. Проверить разрешение имени (`getent ahosts DOMAIN`) и фактический маршрут
   (`ip route get IP`). Наличие `blanc0` означает, что без дополнительного
   правила пакет попадёт в Xray, даже при `curl --noproxy '*'`.
2. Сравнить запрос через TUN/SOCKS и через физический интерфейс. Для второго
   узнать интерфейс командой `ip -4 route show default`, затем выполнить
   `curl --noproxy '*' --interface ИНТЕРФЕЙС https://DOMAIN/`. Это одноразовый
   диагностический запрос без изменения правил.
3. Если физический путь работает, а TUN/SOCKS — нет, проверить политику
   `xray-ctl route show` и срабатывание широкого правила. Если оба
   пути не работают, одного правила `direct` недостаточно; искать DNS,
   транспорт или недоступность сайта.
4. Если SOCKS уже работает, а браузер — нет, проверять его собственный
   proxy/DNS/QUIC, IPv6 и используемые поддомены. Успех одного домена не
   доказывает успех всех ресурсов страницы.

Доменное правило зависит от того, видит ли Xray имя: SOCKS-подключение
передаёт его явно, а в TUN оно определяется по HTTP/TLS/QUIC sniffing.
Приложения с подключением только по IP, скрытым именем или собственным DNS
могут потребовать отдельного анализа. Не добавляйте целый IP-диапазон без
проверки: адреса CDN могут обслуживать множество других сайтов.

Для разбора сбоев есть `xray-ctl route test DOMAIN`: он рекомендует точечное
прямое исключение лишь когда физический путь работает, а оба VPN-пути нет;
при работающем SOCKS и сломанном TUN сначала укажет на сам TUN. Рекомендация
не добавляет правило автоматически и не подменяет проверку браузера.
Дополнительные журналы:
`xray-ctl log --lines 500` (события приложения) и
`xray-ctl log --service` (Xray/systemd). Версия 0.6.3 добавила подробный
журнал приложения; он не появится на системе, где ещё установлена 0.6.2.
Не публикуйте журналы целиком без просмотра на чувствительные данные.

Правила Xray применяются сверху вниз до первого совпадения — этот принцип
описан в [документации Xray](https://xtls.github.io/en/config/routing.html).
Другие клиенты используют ту же схему из списков и приоритетов: см.
[Mihomo](https://wiki.metacubex.one/en/config/rules/) и
[sing-box](https://sing-box.sagernet.org/configuration/route/).
[Список Ozon](https://github.com/v2fly/domain-list-community/blob/master/data/ozon)
поддерживает проект domain-list-community; он не является тестом доступности.
[Категория RU](https://github.com/v2fly/domain-list-community/blob/master/data/category-ru)
включает российские TLD и сервисы. Установленный здесь пакет NekoBox
содержит имена наборов `geosite-category-ru`, `geosite-tld-ru` и `geoip-ru`;
его личные профили и настройки не просматривались. Исходный код
[NekoBox/Nekoray](https://github.com/MatsuriDayo/nekoray/blob/main/db/ConfigBuilder.cpp)
подтверждает отдельные списки для доменов, GeoIP и финальный маршрут.

## Почему `best` мог показать почти все узлы как недоступные

13 октября 2026 года журнал показал подключения временных проверочных Xray к
адресам VPN-серверов внутри `tun-in -> proxy`. Это означало, что при уже
активном `blanc0` кандидат проверялся через текущий VPN. Результаты вида
`failed` для большинства точек и случайные `2/4` в таком режиме не являются
чистой проверкой кандидата.

В 0.6.11 перед `best`, `country` и автоматическим failover добавляются
точечные `throw`-маршруты для всех кэшированных endpoint-адресов. Рабочие
`proxy` и `direct` outbounds Xray дополнительно используют fwmark `4269` и
более приоритетное правило `lookup main`. Модульные тесты и сборка пакета
проверены; длительная работа 0.6.11 на пользовательской машине остаётся
отдельной проверкой после установки.
